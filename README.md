# University Room Fund

Информационная система для учёта аудиторного фонда университета.

Приложение позволяет вести сведения о корпусах, помещениях и подразделениях, рассчитывать общую площадь и вместимость помещений. Система предоставляет веб-интерфейс и HTTP API.

## Назначение системы

Система предназначена для:

- учёта корпусов университета;
- учёта аудиторий и других помещений;
- учёта подразделений;
- хранения площади и вместимости помещений;
- получения сводной информации об аудиторном фонде;
- предотвращения появления некорректных и дублирующихся записей.

## Категории пользователей

### Неавторизованный пользователь

Может:

- открыть страницу входа;
- зарегистрировать учётную запись;
- войти в систему;
- проверить доступность сервиса через служебный адрес.

### Авторизованный пользователь

Может:

- просматривать сведения об аудиторном фонде;
- создавать, изменять и удалять корпуса;
- создавать, изменять и удалять подразделения;
- создавать, изменять и удалять помещения;
- указывать тип помещения;
- отмечать помещение как активное или неактивное;
- просматривать сводные показатели;
- выполнять поиск;
- выйти из системы.

## Основные сценарии

1. Пользователь регистрирует учётную запись.
2. Пользователь входит в систему.
3. Пользователь добавляет корпус.
4. Пользователь добавляет подразделение.
5. Пользователь создаёт помещение и связывает его с корпусом и подразделением.
6. Для помещения можно указать тип и признак активности.
7. Пользователь просматривает сведения об аудиторном фонде.
8. Пользователь изменяет или удаляет существующие записи.
9. Пользователь выходит из системы.

## Правила предметной области

- Номер помещения должен быть уникальным внутри одного корпуса.
- Номер помещения должен содержать от 1 до 20 символов.
- Помещение обязательно должно относиться к существующему корпусу.
- Подразделение, указанное для помещения, должно существовать.
- Площадь помещения должна быть положительным числом.
- Вместимость помещения не может быть отрицательной.
- Операции с аудиторным фондом доступны только авторизованным пользователям.
- Пароли пользователей не хранятся в открытом виде.

- каждое помещение связано с подразделением.

В приложении используется серверная аутентификация на основе сессии.

После успешного входа сервер сохраняет идентификатор пользователя в подписанной cookie сессии. Пароли сохраняются в базе данных только в виде хеша PBKDF2-SHA256.

| --- | --- |

# Лабораторная работа №2. Развертывание в Linux

Для развертывания используются две виртуальные машины Ubuntu Server без графического интерфейса:

- `urf-app` — `192.168.56.10`;
- `urf-db` — `192.168.56.20`.

Сервер приложения запускает FastAPI из виртуального окружения Python и управляется systemd-службой `university-room-fund.service`.

Приложение работает от отдельного системного пользователя `roomfund`, а не от `root`.

PostgreSQL работает на отдельной виртуальной машине.

База данных:

- имя — `university_fund`;
- пользователь приложения — `roomfund_app`.

PostgreSQL принимает подключения к порту `5432` только от сервера приложения `192.168.56.10`.

Настройки приложения хранятся отдельно от исходного кода:

```text
/etc/university-room-fund/app.env
```

Пароли и секреты не хранятся в Git-репозитории.

Разрешённые входящие порты:

- `urf-app`: `22/tcp`, `8000/tcp`;
- `urf-db`: `22/tcp`, `5432/tcp` только от `192.168.56.10`.

Для повторения основных шагов развертывания используются:

- `deploy/app/setup_app.sh`;
- `deploy/app/university-room-fund.service`;
- `deploy/db/setup_db.sh`;
- `deploy/scripts/check_deployment.sh`.

## Тестовая конфигурация

Автоматические тесты выполняются в изолированной тестовой среде и не используют рабочую базу данных приложения.

Для автоматических тестов используется отдельная временная SQLite-база данных. Путь к ней формируется в `tests/conftest.py`.

Перед каждым тестом схема тестовой базы пересоздаётся. Поэтому данные одного теста не влияют на результаты другого.

После завершения тестовой сессии временная база удаляется.

Пример переменных тестовой среды расположен в:

```text
.env.test.example
```

Тестовая конфигурация не содержит реальных производственных учётных данных.

# Правила работы с изменениями

Все результаты лабораторных работ хранятся в одном Git-репозитории.

Для новых функций используется следующий процесс:

```text
задача
  ↓
отдельная Git-ветка
  ↓
изменение кода
  ↓
make verify
  ↓
commit
  ↓
push
  ↓
Pull Request
  ↓
merge в main
```

Запрещается включать изменение в основную ветку только потому, что оно визуально работает. Оно должно пройти заранее определённые проверки.
